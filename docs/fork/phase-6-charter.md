# Phase 6 Charter (Wave 0)

**Status: settled. Do not relitigate.** This document is the _only_ input the
later wave agents are required to read. It is written so that someone who has
read none of the background analysis can implement against it.

Phase 6 of this fork adds six core primitives:

| Key       | Primitive                                                                                     |
| --------- | --------------------------------------------------------------------------------------------- |
| **BBF-3** | Thread lineage — in-place provider change, retired state, lineage-aware timeline              |
| **BBF-4** | Scoped realtime — scoped cross-plugin realtime subscriptions                                  |
| **BBF-5** | Child sessions — native parent/child worker sessions rendered inline in the parent transcript |
| **BBF-6** | Turn telemetry — structured turn/span records emitted by core                                 |
| **BBF-7** | Thread-scoped notifications / inbox                                                           |
| **BBF-8** | Runtime hooks — turn-preflight, provider-event, turn-settled, binding-lifecycle               |

They are implemented by separate agents, partly in parallel. This commit —
Wave 0 — lands _only_ declarations, schema and these decisions. It changes no
behaviour: every column it adds is unread by any code path and every change
kind it adds is unused.

---

## 0. Why the declarations were landed together

Four of the six primitives (BBF-3, BBF-5, BBF-6, BBF-7) each need a drizzle
migration, and **drizzle-kit generation is stateful**. Each run diffs
`packages/db/src/schema.ts` against the latest snapshot in
`packages/db/drizzle/meta/` and appends to `meta/_journal.json`. Two agents
generating concurrently both produce a migration claiming descent from the same
parent snapshot, and the two resulting snapshots cannot be reconciled by text
merge. `validateAppliedMigrationHistory` in `packages/db/src/migrate.ts`
hash-validates the whole chain on startup, so a hand-patched migration fails
against a real `~/.bb` database rather than degrading quietly.

Several plans also collide on the same type declarations —
`packages/domain/src/change-kinds.ts`, `packages/domain/src/thread.ts`, the
`threads` table body and its index block.

So all of it lands once, up front, and the later waves are genuinely disjoint.

## D1. Turn seam — one seam, not two

**BBF-8 owns the EVENT. BBF-6 owns the PAYLOAD.**

- The event is `bb.runtime.onTurnSettled`. Its outcome vocabulary includes
  `delivery-unknown` and `provider-session-lost`.
- The payload is BBF-6's `ThreadTurnRecord`, carried on that event and
  **NULLABLE**. A turn that dies with the provider process never produces a
  `turn/completed` row and therefore has no record — so `delivery-unknown` and
  `provider-session-lost` settlements carry `turn: null`.
- **BBF-6 does NOT add a second per-turn plugin event.** In particular it does
  not add `"turn.completed"` to `PluginThreadEventPayloads`.

Rationale: two seams with different vocabularies is precisely the condition
that produced recall's SHA-pinned fork of telemetry's `spans.ts`. If both
shipped, `bb-plugin-telemetry` and `bb-plugin-recall` would each pick a
different one and disagree about what a turn is.

Consequence for sequencing: **BBF-8 is a hard prerequisite for BBF-6.**

---

## D2. Agent config precedence — spawn-pinned wins for tools and skills

**BBF-5's spawn-pinned configuration is authoritative for which tools and
skills a thread has.**

- BBF-5 pins configuration at thread creation (`agentConfiguration` on the
  create-thread request, persisted in `thread_plugin_agent_configs`). It exists
  to kill board's `spawningReviewerTitles` race, which preflight _cannot_ fix,
  because preflight runs at turn dispatch — after the thread row already
  exists.
- BBF-8's `onTurnPreflight` **may**: add context items, replace bb-controlled
  input, and reject or gate a turn.
- BBF-8's `onTurnPreflight` **MUST NOT** alter tool or skill selection.
- If both are present for one turn, preflight's tool/skill changes are
  **ignored, and the ignore is logged.** Silent precedence is not acceptable
  here; a plugin author must be able to see why their preflight selection did
  nothing.

## D3. Child completion announcer — split by audience, exactly one per audience

Three mechanisms were each about to announce the same child completion. The
resolution splits by _audience_:

- **The USER is told once, by a notification row (BBF-7).** One inbox row.
- **The inline child block (BBF-5) shows live status and does NOT announce.**
  It is a status surface, not an announcement.
- **The parent AGENT keeps a system message.** Board's `returnInstruction` is
  addressed at the model, not at the human; deleting it would leave the parent
  agent never learning that findings arrived. This is the change most likely to
  reintroduce the original hack, so it is explicitly preserved.
- **The old queued duplicate announcement to the user is removed.**

Net: one inbox row for the human, one system message for the agent, zero
duplicates.

Sequencing consequence: BBF-7 stays out of
`apps/server/src/services/threads/child-thread-notifications.ts` and
`parent-system-messages.ts`, which BBF-8 touches.

## D4. Disposition model — three distinct dispositions, never conflated

| Disposition            | Meaning                           | Owner         |
| ---------------------- | --------------------------------- | ------------- |
| `archivedAt`           | **The USER archived it.**         | existing core |
| `supersededByThreadId` | **Lineage retired it.**           | BBF-3         |
| `visibility: "hidden"` | **A plugin owns it as a worker.** | BBF-5         |

These are independent. Nothing may collapse two of them into one flag.

**Consequently `threads.reveal` MUST take explicit options
`{ unhide?: boolean, unarchive?: boolean }`**, and must **NOT** default to
un-hiding plugin-owned workers. A single-argument `reveal({ threadId })` that
clears both `visibility: "hidden"` and `archivedAt` would surface dispatch
workers and board reviewers as sidebar peers of their parents the moment
anything revealed a thread.

**BBF-7's single-argument `reveal` shape is rejected for this reason.** (BBF-7's
plan was also internally inconsistent about it: it defined `{threadId}` and
then consumed `threads.reveal({ unhide: false })`. The explicit-options form is
the one that ships.)

## D5. Generated artifacts — regenerated once per wave, by one named agent

`packages/plugin-sdk/bundled-types/*` and
`packages/templates/src/generated/plugin-sdk-dts.generated.ts` are **generated,
checked in, and verified with `--check` during typecheck.** Concurrent
regeneration produces conflicts that can only be resolved by re-running the
generator against a merged contract — i.e. by serializing anyway.

**Rule: they are regenerated ONCE PER WAVE, by a single named agent at wave
close. Never concurrently by wave workers.** A wave worker that finds its
typecheck failing on `bundled-types/... is stale` should leave it stale and
report it; the wave-close agent runs:

```sh
node packages/plugin-sdk/scripts/build-bundled-dts.mjs
node packages/templates/scripts/generate-templates.mjs
```

(Wave 0's regeneration was performed by the Wave 0 charter agent.)

### Standing rule: register new plugin-facing contracts

Any new plugin-facing **slot or contract** must be:

1. registered in the drift maps in
   `apps/server/test/services/plugins/plugin-authoring-docs.test.ts`, **and**
2. documented in the `bb-plugin-authoring` `SKILL.md`
   (`apps/server/src/services/skills/builtin-skills/bb-plugin-authoring/SKILL.md`).

This is not optional bookkeeping: the fork already shipped `transcriptPrelude`
without doing either and broke the full typecheck.

## 2. Pre-conditions flagged by the sequencing analysis

**BBF-4 — hub routing gate.** BBF-4 must **not** flip hub routing before a test
proves that `plugin-channel` targets replay through `WebSocketManager.onopen`.
Without that test, a `bb connect` tunnel drop silently kills every remote
plugin panel: the socket reconnects, the plugin-channel subscriptions are not
re-sent, and nothing surfaces an error.

**BBF-5 — hierarchy pre-conditions.** Board reviewers are currently _root_
threads, not children. Making them real hierarchy children drags in three
unrelated core behaviours at once, and all three must be resolved **before**
that change lands, not after:

1. `MAX_THREAD_HIERARCHY_DEPTH` (`apps/server/src/services/threads/thread-parent.ts`)
2. duplicate parent system messages (`isParentNotifiableChildThread`, same file)
3. `requireChildThreadsConfirmation` archive prompts

## 4. Reconciliations made while landing this commit

- **`child_kind` column type.** BBF-5 wants a regex-validated slug schema in a
  new `packages/domain/src/thread-child-kind.ts` so the DB layer can import it
  without pulling the domain barrel into drizzle-kit. Wave 0 landed the column
  as plain `text("child_kind")` and left the domain module to BBF-5: the module
  is uncontested (no other primitive touches it) and adding it here would have
  meant landing validation code, which is behaviour.
- **`thread_turns.project_id` is a plain column, not a FK.** BBF-6 specifies
  only the `thread_id → threads.id ON DELETE CASCADE` edge, and inherits
  project-scope isolation and project-delete cleanup through it rather than
  re-implementing them. `project_id` is denormalised purely to serve the
  `(project_id, completed_at)` and `(project_id, model, completed_at)`
  aggregate indexes.
- **`thread_turns.usage_cost_usd` is present and always NULL.** The column
  exists so a price table can be applied later without a migration.
- **Optional, not required, domain fields.** BBF-5 specifies
  `childKind: z.string().nullable()` and BBF-7 specifies
  `unreadNotificationCount: z.number()`. Landing either as _required_ would
  have forced every existing thread mapper to produce it — i.e. behaviour.
  Wave 0 landed all three new fields as optional; the owning wave tightens its
  own field when it starts populating it.
- **Realtime cache registry entries are empty on purpose.**
  `apps/app/src/hooks/cache-owners/realtime-cache-registry.ts` types the thread
  registry as `Record<ThreadChangeKind, ThreadChangeRule>`, so a new change kind
  _must_ have an entry. The two new entries have `dirty: []` and are listed in
  `CHARTER_RESERVED_THREAD_CHANGE_KINDS` /
  `CHARTER_RESERVED_SYSTEM_CHANGE_KINDS` in
  `apps/app/src/hooks/realtime-cache-effects.test.ts`, which otherwise asserts
  that every change kind maps to at least one dirty handler. **The owning wave
  wires its handlers and deletes its kind from that set.**
- **`packages/db/test/migrate.test.ts` needs a rewind helper for every new
  migration.** Several tests migrate to head, rewind the schema to a legacy
  state, clear journal rows and re-apply forward. Wave 0 added
  `dropPhase6CharterSchema(db)` and called it at all six rewind sites. **Any
  later fork migration must add its own drop helper there**, or those tests
  fail with `SQLITE_ERROR` on a `CREATE TABLE` that already exists.

## 6. The reserved `0900_` migration band

Fork migrations are numbered from **0900**, not from the next upstream number.

Upstream's latest migration when this landed was `0099_flawless_maximus`. Had
the charter migration been generated as `0100_*`, upstream's own next migration
would also be `0100_*`, and a rebase would collide on the filename, the journal
entry and the snapshot simultaneously. Numbering from 0900 means an upstream
`0100_*`…`0899_*` can arrive and merge as a plain journal insertion.

Mechanics, for whoever adds the next fork migration:

1. Generate normally: `pnpm --filter @bb/db exec drizzle-kit generate --name=<name>`.
   drizzle-kit allocates `idx = lastJournalEntry.idx + 1` and names both the
   `.sql` and the `meta/NNNN_snapshot.json` from it — so once the journal's last
   `idx` is 900, the next generation is already `0901`. No renaming is needed
   after the first one.
2. Verify the chain by re-running `drizzle-kit generate`; it must print
   `No schema changes, nothing to migrate`.
3. Verify the migration applies to a _copy_ of a real database. Never against
   `~/.bb`, and never with `pnpm reset`.

The one-time cost of the band: `packages/db/test/migration-journal.test.ts`
used to assert `idx === array position`. It now asserts what the snapshot
lookup and drizzle-kit's allocation rule actually need — unique, strictly
increasing `idx` in journal order, and a migration tag whose numeric prefix
matches its `idx`. Migration _apply order_ is journal order and is unaffected:
`readMigrationFiles` in drizzle-orm reads each entry by `tag`, in journal
order, and never looks at `idx`.
